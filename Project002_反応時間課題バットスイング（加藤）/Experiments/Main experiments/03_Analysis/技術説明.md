## 3. トラブルシューティング記録

### 3.1 `S01_free0001.mat` が見つからずエラーになる

**原因**
`x2_import_data.m` が `nTrial = 15` を決め打ちし、`1:nTrial` でファイル名を組み立てていた。しかし本実験 S01 の `free` 条件は 14 ファイルで、番号も 0002〜0014, 0016 と欠番・飛び番がある（計測のやり直しによるもの）。存在しない `S01_free0001.mat` を `load` しようとして落ちる。

**切り分け**
`04_Data/2026-0810_S01/` のファイルを条件別に数えたところ、`simple`/`gonogo`/`gostop` は 15 個で連番、`free` だけ 14 個で欠番があることを確認した。

**解決策**
条件ごとに `dir(fullfile(rawDataFolder, sprintf('S%02d_%s*.mat', iSubject, conditionName)))` でファイルを列挙し、ファイル名末尾4桁から実際の試行番号を取り出してループを回すよう変更。`X.TrialNumber` にはファイル名上の番号を格納する。

**派生する注意点**
条件によって試行数が違うと、`DataArray(iTrial, iCondition)` の構造体配列に空の余り要素ができる。これを後段で判別できるよう、取り込み後に `ErrorCode = Prm.ErrorCode.NoData`（= 3）を入れている。`x4_analyze_single_trial.m` はこの要素をスキップし、`x6_analyze_multi_trial.m` は結果テーブルに含めない。

### 3.2 gostop 条件の Stop 試行が、すべて Go と判定されていた

**原因**
`demo_5_4_gostop_main_experiments.m` の LED 出力波形は、**stop 試行でも必ず先に go cue（+5V, 0.1 s）を出す**設計になっている。

```
go 試行  : ... [+5V 0.1s] [0V 0.25s] [+5V 0.5s] ...
stop 試行: ... [+5V 0.1s] [0V 0.25s] [-5V 0.5s] ...
```

一方 `m3_analyze_single_trial.m` は

```matlab
tCueGo = find(led_cue > 2, 1, 'first') ;
if ~isempty(tCueGo)   % ← 先に見てしまう
```

と、正のパルスを最初に探して見つかれば即 Go と確定していた。そのため stop 試行でも冒頭の go cue が引っかかり、**gostop の全試行が `CueText = 'Go'`** になっていた。

Go/Nogo 課題は正か負のどちらか一方しかパルスが出ないため、この書き方でも問題が表面化しなかった。

**切り分け**
`02_Script/demo_5_4_gostop_main_experiments.m` の `waveform1` を go / stop の両ケースで比較し、両者とも先頭に `voltage_go` が入っていることを確認した。あわせて `demo_5_4_gonogo_main_experiments.m` は単一パルスであることも確認した。

**解決策**
`m3_analyze_single_trial.m` のキュー判定を「正のパルスの後に負のパルスが続くか」を見る形に変更した。

```matlab
tCueGo  = find(led_cue > Prm.Cue.GoThresholdV,  1, 'first') ;
tCueNeg = find(led_cue < Prm.Cue.NegThresholdV, 1, 'first') ;

if ~isempty(tCueGo) && (isempty(tCueNeg) || tCueNeg > tCueGo)
    tCueAnalog = tCueGo ;                       % 起点は go cue のまま
    stopWin = round(Prm.Cue.StopWinSec * Data.AnalogFs) ;
    if ~isempty(tCueNeg) && (tCueNeg - tCueGo) <= stopWin
        cueCode = Prm.CueCode.Stop ; cueText = 'Stop' ;
    else
        cueCode = Prm.CueCode.Go ;   cueText = 'Go' ;
    end
elseif ~isempty(tCueNeg)
    tCueAnalog = tCueNeg ;
    cueCode = Prm.CueCode.NoGo ;     cueText = 'NoGo' ;
end
```

判定窓 `Prm.Cue.StopWinSec = 1.0`（秒）は `parameters.m` で設定する。実験スクリプト上の分岐は go cue の 0.35 秒後（`first_go_signal_duration` 0.1 + `go_to_branch_off_duration` 0.25）なので、1.0 秒は十分な余裕がある。

**残る確認事項**
実データで `CueText` の内訳がプロトコール CSV（`02_Script/CSV/2026-0810/gostop_main_12trials.csv`：go 8 / stop 4）と一致するかを、`x5_check_single_trial_results.m` で目視確認すること。

### 3.3 `x7_3_visualize_grf.m` で床反力の時系列（figure 3〜10）が空になる

**現象**
S01 の解析で、ピーク Fz の箱ひげ図（figure 1）と散布図（figure 2）は描画されるが、GRF 時系列の figure（条件別・正規化前/後の計 8 枚）が空のまま出てくる。エラーは出ない。

**原因**
時系列の描画窓 `plotRange = [-1, 3]`（LED キューの 1 秒前〜3 秒後、計 4.0 秒）が、**計測データの長さを超えている**。

- アナログ記録長：5000 サンプル @ 1000 Hz = **5.0 秒**
- LED キューの位置：**2284〜2884 サンプル（2.28〜2.88 秒）**

したがって切り出し終端は

```
iEnd = tCueAnalog - 1000 + 4000 - 1 = tCueAnalog + 2999 → 5283〜5883 サンプル
```

となり、常に 5000 を超える。`x7_3_visualize_grf.m` の

```matlab
if iStart < 1 || iEnd > nAnalog
    continue
end
```

で**全試行が `continue` され**、`Fz1_raw_cell` が空のまま `if isempty(Fz1_raw_cell), continue, end` に到達するため、plot が一度も呼ばれない。空の figure だけが `clf` されて残る。

**切り分け**
`x2_Data/Data01.mat` と `x5_.../SingleTrialAnalysisResults01.mat` を読み、全 60 要素について除外理由を数え上げた結果：

| 条件 | notGo | Force1 なし | TCueMarker=NaN | iStart&lt;1 | **iEnd&gt;nAnalog** | 描画される試行 |
| --- | --- | --- | --- | --- | --- | --- |
| free | 1 | 1 | 1 | 0 | **14** | 0 |
| simple | 0 | 0 | 0 | 0 | **15** | 0 |
| gonogo | 5 | 0 | 0 | 0 | **15** | 0 |
| gostop | 5 | 0 | 0 | 0 | **15** | 0 |

`Force1`/`Force2`/`Moment1`/`Moment2` は `DataArray` に正しく格納されており（生データの `Force` 構造体も 2 プレート分・5000 サンプルが存在）、**データ側の欠損ではない**ことを確認した。除外は 100% が `iEnd > nAnalog` によるもの。

**解決策**
描画窓をキュー後 2 秒に縮める。

```matlab
plotRange = [-1, 2] ;   % [-1, 3] から変更
```

このとき `iStart = tCue-1000 ∈ [1284, 1884]`、`iEnd = tCue+1999 ∈ [4283, 4883]` となり、全 Go 試行が 5000 サンプルの範囲に収まる。ピーク Fz の集計窓（`swingRange = tCue : tCue+2秒`）とも整合する。

**補足**
`x7_4_visualize_grf_new.m` は同じ 5.0 秒データでも波形が描ける。固定長で切り出さず、共通時間軸 `tWin = -1 : 1/fsA : 2` へ `interp1(..., 'linear', NaN)` で補間し、範囲外を NaN にする方式をとっているため。`x7_3` も将来的にはこの方式に揃えるのが望ましい。

### 3.4 simple 条件の踏み込み足に PeakFz2 = 5.8 BW の外れ値が出る

**現象**
`x7_3_visualize_grf.m` の箱ひげ図で、simple 条件のプレート2（踏み込み足）に 1 点だけ極端な外れ値が出る。

**原因**
値の大小の問題ではなく、**体重正規化の分母が壊れている**。simple 行2（`S01_simple0002.mat`）のベースライン荷重が 158.0 N しかなく、他14試行の 719〜723 N と桁が違う。

| | PeakFz2 | ベースライン荷重 bw |
| --- | --- | --- |
| simple 行2 | 5.805 BW | **158.0 N** |
| simple 他14試行 | 1.13〜1.49 BW | 719〜723 N |

生の `max(Fz2)` は 917 N で、正しい 720 N で割れば 1.27 BW と他試行と同程度である。

**切り分け**
この試行の Fz を 0.25 秒ごとに平均したところ、Fz1+Fz2 の合計が全区間で 150〜190 N のまま体重に一度も達しなかった。Fz1 が負値をとる区間もある。被験者がプレートに正しく乗っていない計測不良の試行であり、値の異常ではなく**試行そのものが無効**。

**解決策**
試行番号のベタ書きではなく、ベースライン荷重の妥当性チェックで弾く。`parameters.m` に

```matlab
Prm.GRF.BWTolerance = 0.2 ;   % 被験者中央値からの許容ずれ（±20%）
```

を追加し、`x7_3_visualize_grf.m` の集計ループの前に全試行のベースライン荷重 `BWArray` を集めるパスを置き、`isBadBW = abs(BWArray - bwRef) > Prm.GRF.BWTolerance * bwRef`（`bwRef` は中央値）で判定する。各ループの `bw <= 0` ガードの直後に `if isBadBW(iTrial, iCondition), continue, end` を入れる。

適用後、simple は n=14、平均 PeakFz2 は 1.601 → 1.315 BW となった。正常試行の中央値からのずれは最大 0.9%、不良試行は 78% で、許容幅 20% には十分な余裕がある。

**補足**
gonogo 行3（1.851 BW）と gostop 行5（2.265 BW）も統計的には外れ値と判定されるが、`bw` は 719〜721 N と正常なので生体力学的なばらつきである。除外してはならない。

同じ不良試行は `x7_4_visualize_grf_new.m` の全指標（力積・RFD・CoP など）も汚染するため、同じ判定パスを入れること（`bw <= 0` ガードは3か所）。

**追記（2026-08-17）：計測不良は3試行あった**

RT 2方式の実装に伴い `x5_SingleTrialAnalysisResultsChecked/` を更新したところ、`CueText` の判定が変わり、`isBadBW` の検出が1試行から3試行に増えた。

```
除外（ベースライン荷重が異常）: simple 行2   bw = 158.0 N
除外（ベースライン荷重が異常）: gonogo 行1   bw =  -8.7 N
除外（ベースライン荷重が異常）: gonogo 行9   bw =  18.7 N
```

gonogo の2試行はベースライン荷重が負値・ほぼ 0 であり、予備実験で S02 に起きていた「ゼロ点ずれ・足位置」の問題（`00_反応時間解析し直し.md` §0.5）と同じ症状である。S01 は「クリーンで除外 0 試行」とされていたが、gonogo 条件では発生していた。本実験の計測手順（プレートのゼロ点補正・足位置固定）への申し送りが S01 にも当てはまる。

この結果、時系列グラフの有効試行数は free 13 / simple 14 / gonogo 9 / gostop 10 となる。

### 3.5 `x4` で「異なる構造体での添字による代入です」が出る

**発生日**: 2026-08-17（§7 の x8 対応にあわせて `m3` にフィールドを追加した直後）

**現象**
`x4_analyze_single_trial.m` を実行すると、free 条件の Trial 11 まで正常に進んだのち、63 行目で落ちる。

```
    Trial 11: エラー "フィールド名 "RASIS" が認識されません。" → スキップ
異なる構造体での添字による代入です。

エラー: x4_analyze_single_trial (行 63)
                SingleTrialResultArray(iTrial, iCondition) = Result ;
```

**原因**
`m3_analyze_single_trial.m` に `BWBase` / `PeakFz1` / `PeakFz2` の3フィールドを追加した際、**`x4` のローカル関数 `makeEmptyResult()` を更新し忘れていた**。

MATLAB の構造体配列は、要素ごとにフィールド集合が完全に一致していないと代入できない（この制約は `x4` の 100〜101 行目のコメントにも書かれている）。したがって

- Trial 1〜10：`m3` が正常に返す → **22 フィールド**の Result が配列に入る
- Trial 11：エラーで `makeEmptyResult()` にフォールバック → **19 フィールド**のまま
- 22 フィールドの配列に 19 フィールドの構造体を代入 → エラー

つまり落ちた直接の原因は Trial 11 のマーカー欠損（§3.3 の `RASIS` 未ラベリング）ではなく、**エラー時フォールバック構造体の定義が古いままだったこと**である。

**解決策**
`makeEmptyResult()` の末尾（`Result.RTForce = NaN ;` の直後）に3行追加する。

```matlab
Result.BWBase          = NaN ;
Result.PeakFz1         = NaN ;
Result.PeakFz2         = NaN ;
```

**フィールド名だけでなく並び順も一致させること。** MATLAB は順序の違いでも同じエラーを出す。上記のとおり末尾に足せば `m3` の正常経路と同順になる。

**派生して見つかった潜在バグ**
`m3_analyze_single_trial.m` の **LED 未検出時の早期 return ブロック**は、正常経路とフィールドの並び順が食い違っている。

| | 正常経路 | 早期 return |
| --- | --- | --- |
| 12番目以降 | `PeakVelHandX` → `TPeakVelHandX` → `SwingOnsetHand` → `RTHand` → `Fz1BaseMean` → `Fz1BaseSD` → … | `Fz1BaseMean` → `Fz1BaseSD` → `PeakVelHandX` → `TPeakVelHandX`（欠落）→ `SwingOnsetHand` → `RTHand` → … |

加えて早期 return 側には `TPeakVelHandX` が設定されていない。**LED が検出できない試行が1つでも出た瞬間に同じエラーが再発する**ため、早期 return ブロックを正常経路と同じ順序に揃えておくこと。現状は全試行で LED が検出できているため表面化していないだけである。

**教訓**
`m3` の出力フィールドを増減させたら、必ず `x4` の `makeEmptyResult()` と `m3` の早期 return ブロックの**3か所すべて**を同じ順序で更新する。

### 3.6 `x9_stats` を実行すると「テキスト文字が正しくありません」

**発生日**: 2026-08-17

**現象**
```
>> x9_stats
エラー: ファイル: x9_stats.m 行: 1 列: 1

cd "Experiments/Main experiments/03_Analysis"
Rscript x9_Statistics/x9_stats.R
```

R のコンソールから実行する場合は、`setwd()` でワーキングディレクトリを `03_Analysis` に合わせてから `source("x9_Statistics/x9_stats.R")`。スクリプトは `03_Analysis` からの相対パスで CSV を読むため、ここを揃えないと `read_csv` が失敗する。

- `install.packages()` で「Please select a CRAN mirror」と聞かれるのはエラーではない。`repos = "https://cloud.r-project.org"` を明示すればプロンプトを回避できる。
- `setwd()` や `library()` は成功時に何も表示しない。無反応は正常であり、失敗すれば必ず `Error` が出る。

## 4. NoGo・Stop 試行の除外方針

NoGo 試行と gostop の Stop 試行は、スイングを抑制することが課題そのものである。したがって**スイング速度・床反力の集計には含めない**。

除外は解析（m3）ではなく可視化スクリプト側で行い、`x4`〜`x6` には全試行を残す。これは、除外の妥当性を後から確認できるようにするため。

各スクリプトの先頭で

```matlab
ExcludedCueTextArray = {'NoGo', 'Stop'} ;
```

を定義し、`ismember(Result.CueText, ExcludedCueTextArray)` で判定する。

| スクリプト | 除外対象 |
| --- | --- |
| `x7_1_visualize_reaction_time.m` | `CueText == "Go"` の行のみ集計（free はキューがないため対象外） |
| `x7_2_visualize_swing_speed.m` | ピーク散布図・箱ひげ図・時系列すべて。参考表示したい場合は `SHOW_EXCLUDED_IN_SCATTER = true` |
| `x7_3_visualize_grf.m` | ピーク Fz の集計・箱ひげ図・散布図・時系列 |
| `x7_4_visualize_grf_new.m` | フォースプレート系指標の箱ひげ図、条件別波形、CoP 軌跡 |

## 5. 反応時間（RT）算出の2方式

**実装日**: 2026-08-17

RT を **Nasu et al. (2020) 準拠の手部速度方式**と**床反力（後ろ足 Fz1）方式**の2方式で算出し、両方をテーブルに並記する。予備実験での検討（`Experiments/Preliminary experiments/2026-0604/MATLAB/00_予備実験解析し直し/00_反応時間解析し直し.md` §0.0）で「Fz1 単独では検出時刻の正しさを検証する手段がない」と結論されたため、身体マーカーによる検出を照合相手として持つことが目的である。

### 5.1 2方式の定義

| | Hand（Nasu 方式） | Force（床反力方式） |
| --- | --- | --- |
| 信号 | 手部重心 − 骨盤重心 の投手方向（+X）速度 | 後ろ足プレートの Fz1 |
| 閾値 | 全スイング試行の**平均ピーク速度の 10%** | 平常時（キュー前0.5秒）から **10 SD** 逸脱 |
| 持続条件 | なし | **30 ms** |
| 検出方向 | ピーク時刻から**時間を遡り**、閾値を下回った最後の点 | 前向きに探索 |
| サンプリング | 250 Hz（マーカー） | 1000 Hz（アナログ） |
| 出力 | `RTHand` / `SwingOnsetHand`（フレーム番号） | `RTForce` / `SwingOnsetForce`（サンプル番号） |

手部・骨盤とも複数マーカーの幾何学的重心を代表点とする（`Prm.RT.HandMarkerNames` / `Prm.RT.PelvisMarkerNames`）。骨盤を引くのは体幹の並進成分を除くため。

ピークから遡って探すのは、前向きに探すと構え・ステップの小さな山を誤検出するためである（`00_RT分析/技術説明.md` §2.3 手順9）。

### 5.2 なぜ2パス構成なのか

Nasu 方式の閾値は「その被験者の**全試行**の平均ピーク速度 × 10%」なので、1試行で完結しない。そこで処理を分けた。

| パス | 場所 | 内容 |
| --- | --- | --- |
| 第1パス | `m3_analyze_single_trial.m` | 手部速度の波形とピーク（`PeakVelHandX` / `TPeakVelHandX`）を出す。閾値は不要 |
| 第2パス | `x4_analyze_single_trial.m` | 全試行のピークから閾値を確定し、`detectHandOnset()` で onset を検出 |

床反力方式は1試行で完結するので `m3` 内で完結する。

RT を `x4` の段階で確定させることで、`x5` の目視確認に両方式の RT が乗る。

### 5.3 実装上の注意点

**閾値の母集団は全条件・全試行（NoGo / Stop を除く）**
条件ごとに平均すると条件差が閾値の差に吸収されるため（`Manuscript/2. Methods/draft.md` §2-4-1 の方針）。free を含めるか迷ったが、実測では free 込み 0.742 m/s / free 抜き 0.757 m/s と差が 2% しかなく、条件別平均も free 6.99 / simple 7.84 / gonogo 7.08 / gostop 7.67 m/s と free が突出していないため、**free 込みで確定**した。

**RT はすべての試行で算出する**
当初は Fz 側だけ Go 試行に限定していたが、2026-08-17 に全試行で算出する方針に変更した。NoGo / Stop でも姿勢制御による荷重変化は生じるため、検出値そのものを見て判断できるようにしておく。どの試行を反応時間として報告するかは下流（x6 以降）で `CueText` 列により選別する。

**構造体配列のフィールド集合は完全一致が必要**
`SingleTrialResultArray(iTrial, iCondition) = Result` は、フィールド名の集合が一致していないと「異なる構造体での添字による代入です」というエラーになる（順序の違いは許容される）。したがって

- `x4` の `makeEmptyResult()` は `m3` の出力と同じ19フィールドを返さなければならない
- 第2パスで新しく足す `SwingOnset` / `RT` は、ループの中で個別に足すとエラーになる。ループの前に `[SingleTrialResultArray.SwingOnset] = deal(NaN) ;` で配列全体に一括で追加する

**`SwingOnset` の単位が方式で違う**
`SwingOnsetHand` は 250 Hz のフレーム番号、`SwingOnsetForce` は 1000 Hz のサンプル番号である。`Prm.RT.PrimaryMethod` による別名 `Result.SwingOnset` だけを見ると取り違えるため、下流では単位の揃っている `RTHand_ms` / `RTForce_ms` を使う。x6 のテーブルにも別名列は入れていない。

## 7. 統計処理用データテーブル（x8）と統計処理（x9）の設計

**設計日**: 2026-08-17

### 7.1 全体方針

ワークフロー ステップ 8・9 に対応する設計。Methods 2-5 で確定した手続き（参加者ごと・条件ごとの平均を代表値とし、条件を要因とする一元配置反復測定分散分析）に、そのまま接続できる形を目標とする。

| ステップ | 内容 | 対応ファイル |
| --- | --- | --- |
| ① | 床反力のピーク値とベースライン荷重を **生値 [N] のまま** 試行単位の結果に追加 | `m3_analyze_single_trial.m` |
| ② | 上記3項目を `ResultsTable` の列にする | `x6_analyze_multi_trial.m` |
| ③ | 被験者内で `isBadBW` を判定 → %BW 正規化 → tidy テーブルと代表値テーブルを CSV 出力 | `x8_make_stat_table.m`（新規） |
| ④ | 正規性 → 反復測定分散分析 → 球面性補正 → 事後検定 → 効果量 | `x9_Statistics/x9_stats.R`（新規） |

対象とする従属変数は Methods 2-5 の表に対応する5指標（反応時間・ピーク合成速度・ピーク投手方向速度・ピーク鉛直床反力の後ろ足／踏み込み足）に限る。`x7_4_visualize_grf_new.m` の指標（後方 GRF・合成 GRF・力積・RFD・体重移動タイミング・CoP 軌跡長）は本文の対象外であり、**統計テーブルには含めない**（2026-08-17 決定。`x7_4` 自体も削除予定）。

### 7.2 正規化を m3 で行わない理由

床反力を %BW に正規化する処理は、あえて `m3_analyze_single_trial.m` には置かない。理由は2つある。

1. **分母の妥当性が単一試行では判定できない。** 計測不良試行の検出（`isBadBW`）は「被験者内の全試行のベースライン荷重の中央値からのずれ」で判定する（§3.4）。1試行だけを見ている `m3` からは中央値が取れない。
2. **分母の差し替えを見越している。** Methods 2-4-3 では、将来 `bw` をプレート出力の和から**実測体重**（`mass_kg * 9.81`）に差し替える方針である。正規化を1か所（`x8`）に集約しておけば、差し替えは1行の修正で済む。

したがって `m3` は生値 `PeakFz1` / `PeakFz2` [N] と `BWBase` [N] だけを出力し、`x8` が正規化と除外を担当する。

### 7.3 床反力への 30 Hz フィルタ

この移設にあわせて、床反力へのローパスフィルタ（2次バターワース・遮断周波数 30 Hz・`filtfilt`）を `m3` 側に実装する。

Methods 2-4-3 は「マーカー座標（`Prm.Fc = 30`）と揃えた 30 Hz でフィルタする」と記述しているが、`x7_3_visualize_grf.m` は `max(Fz1(swingRange))` と**生波形**からピークを取得しており、本文と実装が食い違っていた。ピーク値はフィルタの影響を受けやすいため、統計に用いる値は本文どおりフィルタ済みとする。

`filtfilt` は入力に NaN が1つでもあると出力全体を NaN にするため、フィルタ前に `any(isnan(...))` で弾くこと。

### 7.4 試行の残し方と除外フラグ

§4 の方針（除外は解析側ではなく下流で行い、`x4`〜`x6` には全試行を残す）を `x8` まで延長する。`x8` が出力する試行単位テーブルも**全試行を行として残し**、選別はフラグ列で行う。

| 列 | 意味 |
| --- | --- |
| `IsGo` | `CueText == "Go"`。NoGo・Stop 試行を集計から外すために使う（Methods 2-4） |
| `IsBadBW` | ベースライン荷重が被験者中央値から `Prm.GRF.BWTolerance`（±20%）を超えてずれた試行（§3.4） |
| `n_<指標名>` | 代表値テーブル側。その平均に実際に何試行が入ったかを残す |

`IsBadBW` に該当した試行は `PeakFz1_BW` / `PeakFz2_BW` を NaN にして代表値の平均から外す。RT やスイング速度は床反力の正規化に依存しないため、`IsBadBW` では落とさない。

### 7.5 x8 が出力するファイル

| ファイル | 単位 | 用途 |
| --- | --- | --- |
| `x8_StatTable/StatTable.mat` | — | `TrialTable` と `SubjectTable` の両方 |
| `x8_StatTable/stat_table_trial.csv` | 1行1試行 | 除外の妥当性を後から追うため |
| `x8_StatTable/stat_table_subject.csv` | 1行1被験者×条件 | **R に渡す代表値**（Methods 2-5 (1)） |

代表値は `IsGo` が真の試行のみを対象に `mean(..., 'omitnan')` で算出する。これが Methods 2-5 の「参加者ごと・条件ごとに、対象試行すべての平均値を1つの代表値とする」に対応する。

`free` 条件の反応時間は、Methods 上は分散分析の対象外（反応時間のみ3水準）だが、**テーブルには値を残す**。`x7_1` と同様に検出の妥当性チェック（他条件より明確に遅いはず）に使えるためである。分散分析からの除外は R 側で明示的に行う。

### 7.6 x9（R）の構成

統計ソフトは Methods 2-5 で確定した R 4.3.1 を用いる。`rstatix` パッケージが Methods の手続き (2)〜(7) をすべてカバーする。

| 段階 | 関数 |
| --- | --- |
| (2) 正規性 | `shapiro_test()` |
| (3) 主検定 | `anova_test(dv, wid = Subject, within = Condition, effect.size = "pes")` |
| (4) 球面性 | 上記の戻り値に Mauchly 検定と Greenhouse-Geisser 補正が含まれる。`get_anova_table(correction = "auto")` |
| (5) 事後検定 | `pairwise_t_test(paired = TRUE, p.adjust.method = "bonferroni")` |
| (6) 効果量 | 偏イータ二乗は `effect.size = "pes"`、対比較は `cohens_d(paired = TRUE)` |
| (7) 代替手法 | `friedman_test()` / `friedman_effsize()` / `pairwise_wilcox_test(paired = TRUE)` |

指標ごとに分散分析に含める条件が異なる（反応時間のみ3水準）ため、`dv_spec` で「従属変数名 → 含める条件」の対応を持たせ、同じ処理関数を回す。反復測定なので、全条件が揃っていない被験者はその指標の分析から除く。

### 7.7 被験者が1名の間の扱い

2026-08-17 時点で計測済みの被験者は S01 の1名のみであり、**被験者間の分散が定義できないため反復測定分散分析は実行できない**。R スクリプトは有効被験者数が3名未満の場合、検定を実行せず記述統計のみを出力する。

被験者が増えたら `x8_make_stat_table.m` の `subjects` を更新するだけでよく、R 側は無修正で回る。

パイプラインが正しく組めているかは、S01 の `stat_table_subject.csv` が4行（4条件）になり、`n_PeakFz2_BW` が **free 13 / simple 14 / gonogo 9 / gostop 10**（§3.4 追記の有効試行数）と一致するかで確認できる。

### 7.8 再実行が必要な範囲

### 7.9 S01 での初回実行結果（2026-08-17）

`x2` から `x9` まで通し、`x9_Statistics/x9_stats_result.txt` が生成された。実行環境は R 4.6.0（`tidyverse` 2.0.0 / `rstatix`）。被験者は S01 の1名のみのため、検定は実行されず記述統計のみが出力される（§7.7 のとおり想定内）。

**有効試行数は §3.4 追記の期待値と一部食い違った。**

| 条件 | Go 試行 | 期待（§3.4） | 実際の `n_PeakFz2_BW` |
| --- | --- | --- | --- |
| free | 13 | 13 | 13 ✓ |
| simple | 15 | 14 | 14 ✓ |
| gonogo | 10 | 9 | **8** |
| gostop | 10 | 10 | **9** |

差の内訳は、gonogo Trial 5 と gostop Trial 5 の `BWBase_N` が NaN になっていること。§7.3 で新設した「`filtfilt` の前に NaN を弾く」ガードに掛かったもので、該当試行の床反力データに欠損があることを意味する。

**従来の `x7_3` はこの2試行を除外していなかった。** `max()` が NaN を無視する MATLAB の仕様により、欠損を含んだままピーク値を算出していたためである。新しいパイプラインのほうが正しい挙動だが、gonogo が n=8 まで減るため、欠損がデータのどこに・どれだけあるのかは別途確認すること。

### 7.10 RT 2方式で条件の順序が逆転している（重要）

初回実行の代表値で、**RTHand と RTForce の条件の順序が食い違う**ことが判明した。

| 方式 | simple | gonogo | gostop | 順序 |
| --- | --- | --- | --- | --- |
| RTHand（Nasu 方式） | 583 ms | 623 ms | 665 ms | simple < gonogo < gostop（仮説どおり） |
| RTForce（床反力方式） | 483 ms | **460 ms** | 517 ms | **gonogo < simple** < gostop（理論的にありえない） |

判断が加わる Go/No-Go 課題が単純反応課題より速くなることはないため、RTForce 側の検出に問題がある。

**試行単位のばらつきを見ると原因が絞れる。**

| 条件 | RTForce | RTHand |
| --- | --- | --- |
| simple | 483 ± 80 ms（最小 287） | 583 ± 42 ms（最小 536） |
| gonogo | 460 ± **150** ms（最小 **231**） | 623 ± 84 ms（最小 460） |
| gostop | 517 ± **156** ms（最小 **107**） | 665 ± 59 ms（最小 540） |

RTForce のみ SD が倍近く大きく、生理的にありえない短い値が混じる。350 ms を下回る試行は gonogo に3件（231・244・325 ms）、gostop に1件（107 ms）あり、gostop の 107 ms は `Prm.RT.FloorMs = 150` すら下回る。この短い値が gonogo の平均を押し下げ、順序を逆転させている。

**ベースライン荷重の不良試行が原因ではない。** `IsBadBW` の該当試行を除いても gonogo の平均は 459.5 → 455.9 ms とほぼ動かず、順序も変わらない。

したがって原因は **`Prm.RT.FzK = 10`（ベースライン SD の10倍）という閾値**であり、キュー直後の姿勢調整を動作開始として誤検出していると考えられる。§5 に記した「手部という照合相手ができたことで初めて `FzK` を定量的に評価できる状態になった」という指摘が、実データで裏づけられた形である。

**現在 `Prm.RT.PrimaryMethod = 'Force'` であり、主指標が不安定なほうの方式になっている。** `FzK` の見直しか、主指標を `'Hand'` に切り替えるかの判断が必要（§8 参照）。

## 8. 既知の未解決事項

- **【最優先】`Prm.RT.FzK = 10` の見直し、または主指標の切り替え。** §7.10 のとおり、RTForce は生理的にありえない短い値を出し、条件の順序を逆転させている。RTHand と照合しながら `FzK` を再設定するか、`Prm.RT.PrimaryMethod` を `'Hand'` に変更するかを決めること。統計の主要指標に直結するため、被験者を増やす前に決着させるのが望ましい。

- **`x7_3` のピーク Fz が 30 Hz フィルタを通していない。** §7.3 のとおり `m3` 側にはフィルタを実装するため、`x7_3` の箱ひげ図・散布図の値と統計に用いる値が食い違うことになる。`x7_3` にも同じフィルタを入れるか、`x7_3` 自体を `x8_StatTable` のテーブルを読む形に作り直して二重計算をなくすかを決めること。後者のほうが、正規化と除外の判定が1か所に集約されて望ましい。
- **床反力の正規化の分母が実測体重になっていない。** 現状は `BWBase`（静止時の Fz1+Fz2）で除している。Methods 2-4-3 は実測体重（`mass_kg * 9.81`）で除す方針であり、参加者ごとの体重を解析側に渡す仕組み（被験者情報テーブル等）を用意する必要がある。差し替え箇所は `x8_make_stat_table.m` の `PeakFz1_BW` / `PeakFz2_BW` の算出行のみ。
- **RT 算出にベースライン荷重のガードがない。** `x7_3` は `isBadBW` で計測不良試行を除外するが、`m3_analyze_single_trial.m` の `RTForce` にはこの判定が入っていない。実際、gonogo 行1 は `bw = -8.7 N` にもかかわらず `RTForce = 244 ms` を出力している。ベースラインが壊れている試行の Fz1 由来 RT は信用できないため、同種のガードを RT 側にも入れるか検討すること。
