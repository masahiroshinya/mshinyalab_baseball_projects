# 5.4. 時系列データ可視化関数 ── 段取り

`Experiments/Main experiments/03_Analysis/` に、時系列データをプロットする汎用関数を新規作成するための作業手順書です。

**「層（そう）」**というのは、役割ごとに関数を段違いに分けた、その1段のことです。ここでは3段に分けます。

| 層の呼び名 | やること | たとえるなら |
|-----------|---------|------------|
| **指標層** | 「反応時間を見るとは、どの信号を並べることか」を決める | 献立を決める人 |
| **汎用層** | 渡されたものを、ただ描く | 言われたとおりに調理する人 |
| **変換層** | 番号を秒に直す | 単位を換算する道具 |

3層に分ける理由は、**「どの信号か」と「どう描くか」を分離する**ためです。他指標に応用するときに書き足すのは 3 の層だけになり、1 と 2 は触らずに済みます。

```
x5_check_single_trial_results.m      ← 試行ループ・保存の判断
        │  Data, Result, Prm を渡す
        ▼
plot_rt_detection.m                  ← 「RT を見るとはどの信号を並べることか」を定義
        │  波形・縦線・横線を秒単位で組み立てる
        ▼
plot_time_series.m ← time_from_cue.m ← 「描く」だけ。指標のことは何も知らない
        │
        ▼
lineplot.m（既存）                    ← 縦線・横線の実描画
```

## STEP 0: 前提の確認（コードを書く前に読む）

この節は設計の土台です。ここを飛ばすと、後述の**サンプリング周波数の取り違え**でほぼ確実に事故ります。

### 0-1. データは2つのサンプリング周波数を持つ

**サンプリング周波数**とは「1秒間に何回データを記録したか」で、単位は Hz（ヘルツ）です。250 Hz なら 1 秒間に 250 個の値が並びます。以降 `fs` と略します。

本実験のデータは、**記録の速さが違う2系統が混ざっています**。カメラで撮るマーカーの座標は 250 Hz、電圧として記録する LED 信号と床反力は 1000 Hz です。

| 系統       | 周波数の取得元     | 実測値（S01） | 何が入っているか                                                                      |
| ---------- | ------------------ | ------------- | ------------------------------------------------------------------------------------- |
| マーカー系 | `Data.FrameRate` | 250 Hz        | マーカー座標、そこから作った速度（`VelHandX`, `NetVelTop`, `VelTopX`）          |
| アナログ系 | `Data.AnalogFs`  | 1000 Hz       | LED 信号（`Data.LEDData`）、床反力（`Data.Force1/2`, `Result.Fz1Filt/Fz2Filt`） |

**同じ「時刻」でも、系統が違えば番号が違います。** たとえば「試行開始から1秒後」は、マーカー系では 251 個目ですが、アナログ系では 1001 個目です。この「何個目か」を表す整数を、本書では**フレーム番号**（マーカー系）／**サンプル番号**（アナログ系）と呼びます。

一方の番号をもう一方に直す計算は、次の1行だけです。

```matlab
tCueAnalog = round(Result.TCueMarker / Data.FrameRate * Data.AnalogFs) ;
```

### 0-2. 描きたい信号の一覧（`Result` / `Data` のどこにあるか）

| 信号                     | 変数                  | 系統     | 単位 | 備考                                                          |
| ------------------------ | --------------------- | -------- | ---- | ------------------------------------------------------------- |
| 手部の投手方向速度       | `Result.VelHandX`   | マーカー | m/s  | 骨盤基準。Nasu 方式の RT はこれで検出                         |
| 後ろ足の鉛直床反力       | `Result.Fz1Filt`    | アナログ | N    | 30 Hz フィルタ済み。床反力方式の RT はこれで検出              |
| 踏み込み足の鉛直床反力   | `Result.Fz2Filt`    | アナログ | N    |                                                               |
| LED 信号                 | `Data.LEDData(:,2)` | アナログ | V    | ch2 = cue。正=Go（緑）／負=NoGo・Stop（赤）。ch1 は ready cue |
| バット先端の合成速度     | `Result.NetVelTop`  | マーカー | m/s  | 応用先                                                        |
| バット先端の投手方向速度 | `Result.VelTopX`    | マーカー | m/s  | 応用先                                                        |

### 0-3. 描きたいイベント（縦線）の一覧

ここでいう**イベント**とは、「時間軸上の一点で起きた出来事」のことです（LED が点いた瞬間、動き出した瞬間、速度が最大になった瞬間）。図では**縦線**で表します。

| イベント               | 変数                       | 系統                               | 備考                   |
| ---------------------- | -------------------------- | ---------------------------------- | ---------------------- |
| LED キュー             | `Result.TCueMarker`      | マーカー                           | これを時刻 0 にする    |
| 動作開始（Nasu 方式）  | `Result.SwingOnsetHand`  | **マーカー（フレーム番号）** |                        |
| 動作開始（床反力方式） | `Result.SwingOnsetForce` | **アナログ（サンプル番号）** |                        |
| 手部速度のピーク       | `Result.TPeakVelHandX`   | マーカー                           | onset を遡って探す起点 |
| バット先端速度のピーク | `Result.TPeakVelTop`     | マーカー                           | 応用先                 |

> ⚠️ **最大の罠**：`SwingOnsetHand` は 250 Hz のフレーム番号、`SwingOnsetForce` は 1000 Hz のサンプル番号です（`技術説明.md` §5.3）。どちらも「試行先頭からの位置」ですが、同じ数値でも指す時刻が4倍違います。`Result.SwingOnset`（`Prm.RT.PrimaryMethod` による別名）だけを見ると、どちらの単位かわかりません。**可視化では別名を使わず、必ず `SwingOnsetHand` / `SwingOnsetForce` を明示的に扱うこと。**

### 0-4. 描きたい閾値（横線）の一覧

**閾値（しきいち）**とは、「この値を超えたら動き出したとみなす」という境目の値です。RT の検出はすべて「信号が閾値を超えた時刻を探す」という形をしているので、**閾値の線を図に描けば、検出が妥当かどうかを目で確かめられます。** 値は縦軸の高さなので、図では**横線**になります。

| 方式       | 閾値の値                                                       | どこから取るか                                                                              |
| ---------- | -------------------------------------------------------------- | ------------------------------------------------------------------------------------------- |
| 床反力方式 | `Fz1BaseMean ± Prm.RT.FzK * Fz1BaseSD`（**上下2本**） | `Result` に保存済み。試行ごとに違う                                                       |
| Nasu 方式  | `Prm.RT.HandThrRatio × 全試行の平均ピーク速度`（1本）       | `Result.ThrVelHandX`。**STEP 1-3 案B で `x4` に追加する**。被験者内で全試行同じ値 |

床反力方式の判定式 `abs(Fz1 - mu) > k*sd` を日本語にすると、「Fz1 が平常時の平均 `mu` から、**上にでも下にでも**、平常時のばらつき `sd` の `k` 倍より大きく外れたら」という意味です（`abs` は絶対値＝符号を無視する命令）。上下どちらのずれも拾うので、閾値線は上下2本になります。片側だけ描くと「線を超えていないのに onset が立っている」ように見えて混乱します。

### 0-5. 既存コードから引き継ぐ描画の作法

`x7_3_visualize_grf.m` と `技術説明.md` §3.3・§6 で確定済みの方針です。新しい関数もこれに従います。

- **波形は全体を渡し、表示範囲は `XLim`（横軸の表示範囲）で決める。** 固定長で切り出すと、データ長を超えた試行が全部除外されて図が空になります（実際に起きた事故：`技術説明.md` §3.3）。
- **値の再計算をしない。** `m3` が計算済みの波形（`Fz1Filt` など）をそのまま描きます。生データから描き直すと、フィルタの有無で統計値と食い違います。
- **縦線・横線は既存の `lineplot.m` を使う。** `lineplot(0,'v','k--')` で `XLim`/`YLim` を保ったまま端から端まで線を引けます。
- 凡例（＝どの線が何かを示す説明box）は、重ね描きの1本目にだけ `DisplayName`（凡例に出す名前）を付け、2本目以降は `'HandleVisibility','off'`（凡例に出さない）にします。同じ色の線を12本重ねると、そのままでは凡例に同じ項目が12個並んでしまうためです。

### 1-3. 決着済みの論点：Nasu 方式の閾値をどこから取るか

**問題**：Nasu 方式の閾値 `thrVelHand` は `x4_analyze_single_trial.m` の第2パスで計算されますが、**ローカル変数のまま捨てられており、`Result` にも `Prm` にも残りません**。そのため可視化側が「検出に使われた閾値」を知る手段がありませんでした。

検討した案は2つ。

| 案                                  | 内容                                                                                       | 長所                                           | 短所                                                                 |
| ----------------------------------- | ------------------------------------------------------------------------------------------ | ---------------------------------------------- | -------------------------------------------------------------------- |
| 案A                                 | 可視化スクリプト側で`SingleTrialResultArray` 全体から再計算する                          | `03_Analysis` の既存コードを変更しなくてよい | x4 と同じ計算を2か所に持つことになる。片方だけ直すと図と検出がずれる |

#### 1-3-2. 実装上の注意（3点）

前提として、`x4` は全試行の処理を**2周に分けて**行っています。本書ではこれを**第1パス／第2パス**と呼びます（パス = pass = 1回通ること）。

| | やること | なぜ分けるか |
|---|---------|------------|
| 第1パス | 1試行ずつ `m3_analyze_single_trial` を呼び、結果を配列に詰める | 1試行で完結する計算 |
| 第2パス | 全試行のピーク速度から閾値を決め、それを使って onset を検出する | 閾値が「全試行の平均」なので、**全試行が揃うまで計算できない** |

1. **`makeEmptyResult()` には追加しない。** 一見「フィールドを増やしたら空の Result にも足す」のが筋に見えますが、逆です。`makeEmptyResult` が使われるのは**第1パスの中**（試行ループ内で `SingleTrialResultArray(iTrial, iCondition) = Result` を行うとき）であり、そこでのフィールド集合は `m3_analyze_single_trial.m` の出力と**完全一致していなければなりません**。`ThrVelHandX` を `makeEmptyResult` にだけ足すと、m3 の出力と食い違って「異なる構造体での添字による代入です」で落ちます（`技術説明.md` §3.5）。既存の `SwingOnset` / `RT` も同じ理由で `makeEmptyResult` に入っていません。

## STEP 2: 関数の設計

### 2-1. `time_from_cue.m`（変換層）

**この関数がやること**：「何個目のデータか」という整数を、「キューから何秒後か」という秒に直します。

```
   入力： 251（フレーム番号）, 101（キューのフレーム番号）, 250（fs）
   出力： (251 - 101) / 250 = 0.6 秒
```

つまり「キューから 0.6 秒後」。グラフの横軸に使える値になります。

1行で書けますが、**これを関数にすることで fs の取り違えが起きる場所を1か所に閉じ込められます。**

```matlab
function t = time_from_cue(idx, idxZero, fs)

% time_from_cue  サンプル番号を、基準点を 0 とする時刻 [s] に変換する
%
%   t = time_from_cue(idx, idxZero, fs)
%
%   idx     : サンプル（またはフレーム）番号。ベクトルでもスカラでもよい
%   idxZero : 時刻 0 とするサンプル番号（通常はキュー）
%   fs      : idx と idxZero が属する系統のサンプリング周波数 [Hz]
%   t       : 秒。idx と同じ大きさ
%
%   ※ idx・idxZero・fs は必ず同じ系統（マーカー系 or アナログ系）で揃えること。
%     マーカーのフレーム番号にアナログの fs を渡すと、4倍ずれた図が
%     エラーを出さずに描かれる（技術説明 §5.3）。
%
%   idxZero が NaN のときは、試行先頭を 0 とする絶対時間を返す。
%   これにより、LED 未検出の試行でも図が描ける（要件 R5）。

if isnan(idxZero)
    idxZero = 1 ;
end

t = (idx(:) - idxZero) / fs ;
```

### 2-2. `plot_time_series.m`（汎用層）

**この関数がやること**：渡された波形を1本ずつ描き、指定された位置に縦線と横線を足し、軸ラベルと凡例を付けます。それだけです。**「これは床反力だ」「これは手の速度だ」といった中身のことは一切知りません。** だからこそ、どの指標にも使い回せます。

**設計の要点**：この関数は**秒しか知りません**。フレーム番号もサンプル番号も fs も受け取らず、呼び出し側が `time_from_cue` で秒に直してから渡します。こうすることで、250 Hz の波形と 1000 Hz の波形を同じ図に並べても、時間軸が必ず揃います（要件 R4）。

以下のコードで `%` で始まる行は**コメント**（実行されない説明文）です。MATLAB では関数の先頭に置いたコメントが、`help plot_time_series` と打ったときに表示される説明書になります。

#### 2-2-1. 補足：なぜ `Ax` を引数で受け取るのか

MATLAB の描画は次の入れ子になっています。

```
figure  = ウィンドウそのもの（figure(1) で開くあの窓）
  └ axes = その中の「グラフ1枚分の枠」。目盛り・軸ラベル・描いた線の入れ物
```

`subplot(3,1,1)` は「figure を縦3分割した1番目の枠を作る／選ぶ」命令で、**この枠1つが axes 1個**です。3段のパネルなら axes は3個。`Ax` はその枠を指すハンドル（どの枠のことかを保持する変数）です。

`gca` は **g**et **c**urrent **a**xes の略で、「いま描画対象になっている枠」を返します。普段書く `plot(t,y)` は、実は `plot(gca, t, y)` の省略形です。

**問題は `gca` が「最後に触った枠」を指すこと**です。複数の figure や subplot を扱うと、どれが current かが状況で変わります。

```matlab
% Ax を渡さない設計だと…
subplot(3,1,1)
plot_time_series(SignalHand, OptHand) ;   % ← ここまでは1段目に描かれる

figure(2)                                  % ← 何かの都合で別の figure を開くと
plot_time_series(SignalFz, OptFz) ;        % ← figure 2 に描かれてしまう
```

`Ax` を明示的に渡せば、間に何が挟まっても行き先が確定します。

```matlab
Ax1 = subplot(3,1,1) ;
Ax2 = subplot(3,1,2) ;
Ax3 = subplot(3,1,3) ;

plot_time_series(Ax1, SignalHand, OptHand) ;   % 必ず1段目
plot_time_series(Ax2, SignalFz,   OptFz  ) ;   % 必ず2段目
plot_time_series(Ax3, SignalLED,  OptLED ) ;   % 必ず3段目

linkaxes([Ax1 Ax2 Ax3], 'x') ;   % ← 横軸を連動させるにもハンドルが要る
```

最後の `linkaxes` が決定的な理由です。3段の横軸を連動させる（1段目を拡大すると他も追従する）には、3つの枠のハンドルが手元に残っている必要があります。

**`[]` を渡すと `gca`** というのは、グラフを1枚だけ描く簡単な用途で `Ax = subplot(...)` を書く手間を省くための逃げ道です。実体は関数冒頭の1行だけ。

```matlab
if isempty(Ax), Ax = gca ; end
```

```matlab
figure(1) ; clf
plot_time_series([], SignalHand, OptHand) ;   % 枠を気にせず1枚だけ描く
```

これは新しい発想ではなく、既存の `lineplot.m` が `axescheck` で同じことをしています（第1引数が axes ならそれを使い、違えば `gca`）。作法を揃えた形です。

#### 2-2-2. 実装順序の注意

`lineplot.m` は呼ばれた時点の `XLim` / `YLim` を読んで線を引き、引いた後に元の範囲へ戻します。したがって

1. 波形を `plot`
2. `set(Ax,'XLim',...,'YLim',...)` で範囲を確定
3. `lineplot` で縦線・横線

の順序が必須です。2 を飛ばすと、線が軸いっぱいに伸びなかったり、後から `XLim` を変えた際に線が途中で切れたりします。

```matlab
OptHand.Level(1).Style = {'r-'} ;

% --- 中段：Fz1（アナログ系 fsA / tCueAnalog で揃える）---

SignalFz.t     = time_from_cue((1:nA)', tCueAnalog, fsA) ;    % ← fs ではなく fsA

sd = Result.Fz1BaseSD ;
OptFz.Level(1).y = mu + Prm.RT.FzK * sd ;                     % 上側

```

#### 2-3-2. 上の抜粋に含まれていないもの

実際に `plot_rt_detection.m` を書くときは、2-3-1 の前後に次が必要です。

**（a）`Prm` の読み込み**（抜粋の前）

抜粋の中で `Prm.RT.FzK` を使っているので、その前に読み込んでおく必要があります。

```matlab
Prm = parameters ;
```

**（b）下段（LED パネル）の組み立て**（抜粋の中に入るべきもの）

抜粋では上段（手部速度）と中段（Fz1）しか書いていません。下段の LED も必要で、書き方は中段と同じ**アナログ系**です。

```matlab
% --- 下段：LED 信号（アナログ系 fsA / tCueAnalog で揃える）---
nLED = size(Data.LEDData, 1) ;
SignalLED(1).t = time_from_cue((1:nLED)', tCueAnalog, fsA) ;
SignalLED(1).y = Data.LEDData(:, 1) ;      % ch1 = ready cue

```

**（c）枠を作って描かせる部分**（抜粋の後）

ここが「定型（＝毎回同じ決まりきった書き方）」と呼んでいた部分です。

```matlab
Ax1 = subplot(3,1,1) ;
plot_time_series(Ax1, SignalHand, OptHand) ;

Ax2 = subplot(3,1,2) ;
plot_time_series(Ax2, SignalFz,   OptFz  ) ;

Ax3 = subplot(3,1,3) ;
plot_time_series(Ax3, SignalLED,  OptLED ) ;

linkaxes([Ax1 Ax2 Ax3], 'x') ;   % 3段の横軸を連動させる
```

軸ラベルや表示範囲（`XLim`）は、`OptHand.XLabel` のように `Opt` に入れて `plot_time_series` に任せます（STEP 2-2 の仕様）。

**まとめると、関数全体はこの並びになります。**

```
1. Prm = parameters ;                          ← (a)
2. fs / fsA / tCueMarker / tCueAnalog を用意     ← 2-3-1 の冒頭
3. 上段・中段・下段の Signal と Opt を組み立てる  ← 2-3-1 ＋ (b)
4. subplot で枠を作り、plot_time_series を3回呼ぶ ← (c)
5. linkaxes で横軸を連動させる                   ← (c)
```

## STEP 4: 動作確認

### 4-1. 数値の照合（図を見る前にやる）

**照合**とは、「図に描かれた線の位置」と「計算で出ている数値」が一致するかを突き合わせることです。

図は多少ずれていても「それらしく」見えてしまい、目では気づけません。だから**先に数値で確かめます**。

- [ ] 閾値線の高さ（`Result.ThrVelHandX`）が、`x4_analyze_single_trial.m` 実行時のログの値と一致する
- [ ] 手部の onset 線の位置 [s] × 1000 が `Result.RTHand` [ms] と一致する
- [ ] 床反力の onset 線の位置 [s] × 1000 が `Result.RTForce` [ms] と一致する
- [ ] キュー線が厳密に x = 0 にある

3つ目までがずれていたら、ほぼ確実に fs の取り違え（STEP 0-1）です。**ずれ幅が 4 倍または 1/4 倍なら断定してよい**（250 Hz と 1000 Hz の比）。

### 4-2. 図の目視確認

数値が合っていることを確認したうえで、今度は図を目で見ます。ここで見るのは「値が合っているか」ではなく、**「検出された onset が、波形を見た人間の感覚と合っているか」**です。

`simple` 条件の Go 試行を数試行見て、次を確認します。

- [ ] 手部速度が閾値線を上向きに横切る点と、onset の縦線が一致している
- [ ] `|Fz1 - Fz1BaseMean|` が閾値線を超え、その状態が 30 ms 続いた最初の点に onset の縦線がある
- [ ] 床反力の onset が手部の onset より**早い**（S01 では simple / gonogo / gostop の 35/35 試行で成立。`技術説明.md` §5.4）
- [ ] LED パネルで、ch2 の立ち上がりが x = 0 にある

### 4-3. 異常系の確認（要件 R5）

**異常系**とは、「うまくいかなかった場合」のことです。データが欠けている試行、LED が検出できなかった試行、そもそもスイングしない試行などがこれにあたります。

こうした試行で関数がエラーを出して止まると、**試行ループの途中で確認作業が中断してしまいます**。「描けないものは描かず、描けるものだけ描いて次に進む」という動きになっているかを、実データで確認します。

- [ ] `free` 条件：キューが検出されているか。`CueText` が空の試行があるか
- [ ] `gonogo` の NoGo 試行、`gostop` の Stop 試行：LED が負のパルスになっている。onset が出ていない試行では縦線が描かれない
- [ ] `free` 行11（`S01_free0012.mat`）：骨盤マーカー4点が欠落しており `VelHandX` が異常になっている可能性がある（`技術説明.md` §3.5）。落ちないことを確認する
- [ ] ベースライン荷重が異常な試行（`x7_3` の `isBadBW` に引っかかる試行）
- [ ] 条件間の試行数の差を埋めた欠測要素（`ErrorCode = Prm.ErrorCode.NoData`）

### 4-4. 見つかると期待される所見

`技術説明.md` §5.5 に「床反力方式が早すぎる」試行が挙がっています。**本ツールの最初の実用目的はこれの原因究明です。**

| 試行                     | RTForce    | RTHand   | 見るべき点                                                  |
| ------------------------ | ---------- | -------- | ----------------------------------------------------------- |
| gostop 行10              | 107 ms     | 540 ms   | キュー直後の Fz1 が、10 SD の線をノイズで一瞬超えていないか |
| free 8・13、gonogo 1・10 | 極端に短い | 正常範囲 | 同上                                                        |

`Prm.RT.FzK = 10` が適切かどうかを、この図で初めて目で判断できるようになります。閾値線と波形の関係を見て、`FzK` を上げるべきか、持続時間 `DurMs = 30` を延ばすべきかを判断材料として記録します。
