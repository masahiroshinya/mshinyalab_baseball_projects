## 1. 背景 ― なぜ書き直すのか

現行の `m3_analyze_single_trial.m` は、バット長軸の **角速度** を計算し、
それが 300 deg/s を超えた瞬間をスイング開始として反応時間を算出している。
つまり「反応時間」と「バットの速度指標」が **同じ 1 つの信号から** 出ている構造だった。

今回、比較指標を「バット先端マーカー（top）の並進速度」へ変更する方針としたため、
この構造を見直す必要が生じた。あわせて、これまで m3 が一切扱っていなかった
床反力（Fz）を解析項目に加える。

### [2026-07-16] ステップ1：バット先端の並進速度を計算する（②）― 完了

#### 変更内容

`m3_analyze_single_trial.m` の角速度計算ブロックの前に、並進速度の計算を追加した。

```matlab
% ---- ② バット先端（top）の並進速度 ----
posTop    = M.top / 1000 ;                    % [m]    各列 = x, y, z
velTop    = diff3p(posTop, 1/fs) ;            % [m/s]  中心差分（3点法）
netVelTop = sum(velTop.^2, 2).^0.5 ;          % [m/s]  速度ベクトルのノルム（＝速さ）

Result.NetVelTop  = netVelTop ;               % 速度波形（ステップ2の目視確認用）
Result.PeakVelTop = max(netVelTop) ;          % 試行全体での最大速さ
```

あわせて `x4_analyze_single_trial.m` の `makeEmptyResult()` に
`NetVelTop`（`[]`）と `PeakVelTop`（`NaN`）を追加した。
m3 の出力と食い違うと、エラー試行が出た瞬間に
`SingleTrialResultArray(iTrial, iCondition) = Result` で
「構造体配列のフィールドが一致しない」エラーになるため。

**角速度の計算は暫定的に残した。** ステップ1 の目的は ② を出すことだけで、
RT 検出はまだ角速度に依存しているため、ここで消すとパイプラインが通らない。
ステップ3 で並進速度による検出に切り替えた時点で削除する。

#### 設計判断：なぜ微分の前に mm → m へ直すのか

微分は線形な操作なので、位置を 1000 で割ってから微分しても、
微分してから速度を 1000 で割っても結果は同じ。
しかし **先に割っておくと、以降に出てくる `netVelTop`・`PeakVelTop`・閾値がすべて m/s で統一される**
ため、後で単位を取り違える事故が起きない。
（学習資料 `解析項目学習/バット先端並進速度算出.md` 8.1 で保留にしていた単位の扱いは、これで確定）

#### コードの要点

| 記述                     | 意味                                                                                                                                                                                       |
| ------------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| `diff3p(posTop, 1/fs)` | 第2引数はサンプリング**間隔** h [s] であって周波数ではない。`fs` ではなく `1/fs` を渡す。中身は中心差分＝学習資料3章の差商 (x(t+h) − x(t−h)) / (2h) を全フレームに適用したもの |
| `sum(velTop.^2, 2)`    | `2` は「2次元目（列方向）に足す」の意味。各行ごとに vx²+vy²+vz² を作る                                                                                                                |
| `.^0.5`                | 平方根。結果は速度ベクトルの**ノルム**＝学習資料2章でいう**速さ（スカラー）**。向きの情報はここで捨てられる                                                                    |

#### 検証結果（S01, free 条件, 全20試行）

| Trial | PeakVelTop [m/s] | PeakOmegaDeg [deg/s] |
| ----- | ---------------- | -------------------- |
| 1–20 | 25.8 〜 27.3     | 1771 〜 1872         |

**単位が正しいことの裏付け（角速度との突き合わせ）：**

PeakOmegaDeg ≈ 1800 deg/s をラジアンに直すと 1800 × π/180 ≈ 31.4 rad/s。
剛体の回転では先端速度 v = ω × r（r は回転中心から先端までの距離）なので

    r ≈ 26 [m/s] ÷ 31.4 [rad/s] ≈ 0.83 [m]

これはバットの長さとして妥当。
もし mm のまま微分していたら r = 830 m という物理的にありえない値になっていたため、
`M.top / 1000` が効いていることが確認できた。

また、全20試行が 25.8〜27.3 m/s（ばらつき約 2%）に収まっており、
同一被験者の全力スイングとして再現性が高い。
外れ値がないことは、NaN 補間やローパスフィルタが波形を壊していないことも示唆する。

#### ステップ1 実行時に発見した問題（いずれもステップ1の範囲外）

1. **NoGo 試行で RT が出る（偽陽性）**
   S01 Trial 9 で 7020 ms、S02 で 4728・4936・5220 ms。
   NoGo は「スイングしない」条件なので本来すべて NaN になるべき。
   キューから 4〜7 秒後という値は、被験者が構えを解いてバットを下ろした動作を拾っている。
   原因は探索範囲がキューから試行終了までの全区間になっていること
   （`searchRange = tCueMarker : nFrames`）。
   → **ステップ3 で探索窓に上限（例：キューから 2 秒）を設ける。**
   並進速度に切り替えるとバットを下ろす動作も先端が動くぶん、この偽陽性はむしろ増える方向。
2. **free 条件の RT が異常に長い**
   S01 で 880〜1524 ms（simple は 544〜840 ms）。
   キュー自体はある（CueText が Go）が、free 条件が自分のタイミングで振る課題なら、
   この「RT」は反応時間ではなく単なる待ち時間で、指標として意味を持たない。
   → **free 条件の RT を解析対象に含めるか、ステップ3 までに決定する。**
3. **S02 gonogo Trial 1 がエラーで落ちる**
   「位置 2 のインデックスが配列範囲を超えています」。
   `Data.LEDData(:, 2)` で `LEDData` に2列目が存在しないときに出る形。
   この試行だけアナログの取り込みに失敗している可能性がある。
   切り分け：`size(DataArray(1,3).LEDData)` が `[N 2]` になっているか確認する。
   → ステップ1 とは独立した既存の不具合。原因を特定して `技術説明.md` に記録する。

**重要な発見1：中間の盛り上がりがない ―― ※後にステップ3で撤回。下記の訂正を参照。**
事前に懸念していた「体重移動やステップでバット先端が動き、
ベースラインとスイングの間に中間的な盛り上がりが出る」現象は、この縮尺では **観察されなかった**。

> **【訂正 2026-07-16, ステップ3】この結論は誤りだった。**
> 上の判断は Trial 1 の波形を **縦軸 0〜3 m/s** で見てのものであり、
> **0.17〜1.0 m/s という低い帯域での動きは、この縮尺では見えていなかった。**
> ステップ3 の逆探索の比較で、準備動作（体重移動・構えの揺れ）が実在することが判明した。
> 決定的な証拠は `free Trial 9` の波形（縦軸 0〜1.5 m/s に拡大）で、
> **準備動作（第1段）とスイング（第2段）が明確に分離**していた。
> → 加藤が当初から懸念していた「並進速度は体重移動でも上がる」というリスクは **実在した**。
> → **教訓：波形の観察は、判断したい現象のスケールに合わせて縦軸を絞ること。**

**重要な発見2：従来の角速度300 deg/s は約 260 ms 遅れて検出していた。**
実際の動き出しは t ≈ 0.40 s、角速度による検出は t ≈ 0.66 s。
つまり従来の RT は「スイング開始」ではなく「スイングが十分加速した時刻」を測っていた。
並進速度に切り替えると RT は系統的に短くなる。条件間比較には影響しないが、
**絶対値として報告する場合は解釈が変わる。**

**重要な発見3：立ち上がりが急峻。**

閾値を多少上下させても検出時刻が大きくズレないという、実装上ありがたい性質。

> 「0.5 m/s で余裕がある」と判断しかけた。全試行・全条件を見て初めて

#### 検出アルゴリズムの選択肢（ステップ3 で決定）

**単一閾値の原理的な弱点：** 閾値を上げるほど偽陽性は減るが、検出が遅れて RT が系統的に過大評価される。
1.0 m/s の交差時刻は実際の動き出し（t ≈ 0.40 s）より 100 ms 以上あと。
従来の角速度 300 deg/s が 260 ms 遅れていたのと同じ問題を、程度を軽くして引き継ぐことになる。

**案A：単一閾値**（1.0 m/s を超えた最初の点＝スイング開始）

**案B：逆探索（アンカー＋さかのぼり）**

```matlab
% 1) 「確実にスイングだ」と言える高い閾値でアンカーを取る
idxAnchor = find(v(searchRange) > 1.0, 1, 'first') ;

% 2) そこから過去にさかのぼり、速度がベースライン近傍まで落ちる最後の点を探す
%    → これが真の動作開始
baseLevel = mean(v(baseRange)) + 3*std(v(baseRange)) ;   % 例：0.122 + 3*0.015 ≒ 0.17
idxOnset  = find(v(searchRange(1):idxAnchor) < baseLevel, 1, 'last') ;
```

案B では **偽陽性の棄却は高い閾値（1.0）が担い、時刻の精度は低い基準（0.17）が担う**という分業になる。
NoGo 試行は 1.0 を超えないのでそもそもアンカーが立たず、さかのぼりも起きない。
運動開始検出では標準的な手法。

#### free 条件について ― 証拠が揃った

閾値 0.5 での平均 RT：**free 940 ms / simple 538 ms / gonogo 521 ms**（free だけ約 400 ms 遅い）
角速度法でも free 1129 / simple 688 / gonogo 680 ms で同じ傾向。
加えて free はベースラインが最も高く（最大の最大 0.441）、0.3→0.5 の飛びも最大（-391 ms）。

→ **free 条件では被験者がキューに反応しておらず、自分のタイミングで振っていることを強く示唆する。**
**free の RT は反応時間ではない。**

**決定（2026-07-16）：free の RT は算出はするが、反応時間としては報告しない。**
コード上は3条件を均一に処理して値を残すが、free は「参考値」扱いとし、
条件間の RT 比較（simple vs gonogo）には含めない。
free は ②バット先端並進速度 と ③Fz の比較にのみ使う。

#### 確定した実装

```matlab
win       = tCueMarker : min(tCueMarker + round(2*fs), length(netVelTop)) ;
idxAnchor = find(netVelTop(win) > 1.0, 1, 'first') ;      % 確実にスイングと言える点

if isempty(idxAnchor)
```

### [2026-07-16] ステップ3：S02 での検証 ― **バット先端速度による RT 検出は破綻**

#### 結論

**S02 では、バット先端速度による動作開始の検出が原理的に不可能。**
閾値の調整では直らない。**成立する閾値が存在しない。**

| 制約 | 値 |
|------|-----|
| NoGo を棄却するには、閾値はこれより**上**でなければならない | **1.533 m/s** |
| ところが simple のキュー前ベースラインはここまで達する | **1.154 m/s** |

S01 ではこの2つが 0.589 と 0.441 で、閾値 1.0 がすっぽり収まった。
**S02 ではベースラインがアンカー（1.0）を超えている。**
＝ キューが出る前からバットが 1.0 m/s で動いている試行がある。

#### S01 と S02 の比較 ― 別物だった

| 項目 | S01 | S02 | 比 |
|------|-----|-----|-----|
| ベースライン平均（simple） | 0.103 | **0.240** | 2.3倍 |
| ベースライン最大の最大（simple） | 0.377 | **1.154** | 3.1倍 |
| ベースライン最大の最大（free） | 0.441 | **0.917** | 2.1倍 |
| NoGo 最大 | 0.589 | **1.533** | 2.6倍 |

#### 決定的な証拠

**証拠1：生理的にありえない RT。**
S02 の感度分析で、閾値 0.3 のときの平均 RT が **free 143.4 ms / simple 182.0 ms**。
単純反応時間の生理的下限は約 150 ms なので、**143 ms は物理的にありえない。**
キューに反応する前の動きを測っている。

**証拠2：立ち上がりが急峻でない。**
閾値 0.5 → 2.0 での RT の広がり：

| | S01 simple | S02 simple |
|---|---|---|
| 0.5→2.0 の RT 変化 | 111 ms | **326 ms** |

S01 では「立ち上がりが急峻だから閾値の選択は結果を左右しない」と言えたが、
**S02 では立ち上がりが緩やかで、閾値をどこに置くかで答えが 300 ms 動く。恣意的な選択になる。**

**証拠3：案B-3 が NaN と 0 ms を量産。**
free で 8/20、simple で 5/20 が NaN。さらに 0.0 / 4.0 / 24.0 / 40.0 / 80.0 ms という値。

> NaN と 0.0 は**同じ原因の裏表**。逆探索は「キュー〜アンカーの区間で基準（ピークの1%）を
> 下回る最後の点」を探す。この区間で速度が一度も基準を下回らなければ **NaN**、
> キュー直後だけ下回ってあとは超えっぱなしなら **0.0**。
> どちらも **S02 はキューの時点でバットが止まっていない**ことを意味する。

**証拠4：アンカーが NoGo を棄却できない。**

| Trial | CueText | 案A |
|-------|---------|-----|
| 5 | NoGo | NaN（棄却成功） |
| 9 | NoGo | **1880 ms** |
| 13 | NoGo | **436 ms** |
| 17 | NoGo | **540 ms** |
| 20 | NoGo | **544 ms** |

**5試行中4試行でアンカーが立った。**
Trial 13 の 436 ms・Trial 17 の 540 ms は、Go 試行の案A（364〜576 ms）と区別がつかない。
→ **速度の立ち上がりでは Go と NoGo を分離できない。**

#### 診断

**S02 はバットを常時揺らして構えるタイプの被験者（ワッグル）。**
「静止 → 動き出し」という前提が成立しないため、
「バット先端速度がいつ静止から離れたか」という問い自体に答えがない。

#### 救えるもの・救えないもの

**救える：NoGo 判定 → ピーク速度で判定する（設計変更）**

アンカーに「スイングがあったか」の判定を兼ねさせたのが設計ミスだった。

| 判定方法 | S01 | S02 | 本物のスイング | マージン |
|----------|-----|-----|---------------|---------|
| 立ち上がり（従来） | 0.589 | **1.533** | ― | 紙一重 |
| **ピーク速度（新）** | 0.589 | 1.533 | **約 25 m/s** | **16倍** |

```matlab
% 「スイングがあったか」はピークで判定する（マージンが桁違いに大きい）
if max(netVelTop(win)) < 10          % [m/s] スイングは25m/s、ワッグルは1-3m/s
    RT = NaN ;                       % スイングなし → NoGo
    return
end
% ここから先、スイングがあったことは確定。タイミングの検出に進む。
```

立ち上がりの閾値（0.589 vs 1.0 の紙一重）から、
ピークの閾値（1.5 vs 25 の圧勝）に土俵を移す。**両被験者で同じ基準が使える。**

**救えない：動作開始の検出**
バットが止まらないのだから、閾値をどう選んでも測っているのはワッグルの途中。

#### 方針転換の提案：RT 検出を Fz に移す

セッション冒頭の設計判断（RT 検出の信号として「バット先端の並進速度」を選択）の
**前提（バットは構えで静止している）が S02 で崩れた**ということ。

**Fz に移す利点：**

1. **バットのワッグルは Fz にほとんど影響しない。**
   構えでバットを揺らしても体重は動かないので、Fz のベースラインは静かなはず。
   → S02 のワッグル問題を原理的に回避できる。
2. **すでに計画に入っている。** 解析項目③の Fz には「立ち上がり時刻」が含まれる。
   **それがそのまま RT になる。** ステップ4 の作業が ① と ③ を兼ね、むしろ工数が減る。
3. **体重移動はスイングより先に起こる。** バットが動く前に足が動くので、
   より早い＝より真の反応に近いタイミングが取れる。

**懸念：**

- Fz が拾うのは「動作開始」であって「スイング開始」ではない（定義の変更になる）。
- NoGo 試行で被験者が体重移動を始めてから止まる（**部分反応**）と、Fz は動いてしまう。
  バット速度では見えなかった現象なので、確認が必要。
