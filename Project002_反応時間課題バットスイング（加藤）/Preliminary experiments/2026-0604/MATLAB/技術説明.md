### [2026-06-15] x2_import_data.m：Analog.Data 転置漏れバグ

**発見者：** 加藤 和太郎 (student) / AI (Claude)

**症状：**
- 被験者2（S02）で x4 を実行すると、全60試行で「配列インデックスは正の整数または logical 値でなければなりません」エラーが発生し、RT がすべて NaN になった。
- 被験者1（S01）はクラッシュしなかったが、反応時間が誤った値で算出されていた。

**原因：**
`x2_import_data.m` の LED データ抽出部で、`Analog.Data` の転置が実装されていなかった。
`Analog.Data` は `[チャンネル数 × サンプル数]`（例: 64×12000）で格納されているが、コードでは転置なしに `analogData(:, 1:2)` で列方向を取得していた。そのため、チャンネル番号（64）をサンプル番号として誤認識し、インデックスエラーまたは誤ったタイミング算出が発生した。

コメントには「転置する」と正しく記載されていたが、実装が漏れていた。

**切り分け手順：**
1. S02 の x4 エラーログを確認 → 全試行でインデックスエラー
2. `Data.LEDData` のサイズを診断 → `64×2`（正しくは `12000×2` になるべき）
3. `X.Analog.Data` のサイズを確認 → `64×12000`（転置前の生データ形式）
4. S01 でも同サイズであることを確認 → S01 も転置が必要と判明

**解決策：**
`x2_import_data.m` の `analogData = X.Analog.Data ;` を以下に置き換えた：

```matlab
rawAnalog = X.Analog.Data ;
if size(rawAnalog, 1) < size(rawAnalog, 2)
    rawAnalog = rawAnalog' ;
end
analogData = rawAnalog ;
```

`size` で行列の向きを判定してから転置することで、データ形式が変わっても安全に動作する。

**再処理：**
修正後、`subjects = [1, 2]` で x2 → x3 → x4 → x5 → x6 を再実行し、S01・S02 ともに正しい値に更新した。

### [2026-06-16] x6_analyze_multi_trial.m：保存パスが最終被験者のIDになる設計上の注意点

**発見者：** 加藤 和太郎 (student) / AI (Claude)

**症状：**
`subjects = [1, 2]` で x6 を実行すると、`x6_MultiTrialAnalysisResults/` に `MultiTrialResults02.mat` のみが保存され、`MultiTrialResults01.mat` は上書きされないか、または両被験者のデータが混合した `MultiTrialResults02.mat` が生成される。

**原因：**
`x6_analyze_multi_trial.m` では `ResultsTable` の初期化がループの外にあり、全被験者のデータが1つのテーブルに蓄積される。保存はループ終了後に `iSubject`（= 最後の被験者番号）で1回のみ行われる。

```matlab
ResultsTable = table() ;          % ← ループ外で初期化

for iSubject = subjects           % [1, 2]
    % S01・S02 のデータを ResultsTable に追記
end

% ループ終了後、iSubject = 2 になっている
save(savePath, 'ResultsTable')    % → MultiTrialResults02 に両被験者分が保存される
```

**解決策（当面の運用）：**
被験者ごとに x6 を個別に実行する（`subjects = [1]`、次に `subjects = [2]`）ことで、単一被験者のデータのみが含まれるファイルを生成する。

### [2026-07-16] x4_analyze_single_trial.m：m3 差し替え直後に実行できず、MATLAB 再起動で解消

**発見者：** 加藤 和太郎 (student)

**症状：**
`m3_analyze_single_trial.m` を角速度削除版に差し替えた直後、`x4_analyze_single_trial.m` が
実行できなくなった。**MATLAB を再起動したところ、コードを一切変更せずに実行できた。**

**切り分け：**
AI がファイルの中身を確認したが、m3・x4 とも記述は正しく、整合していた。

- m3 の出力フィールドと x4 の `makeEmptyResult()` は
  `NetVelTop → PeakVelTop → CueCode → CueText → TCueMarker → SwingOnset → RT` の
  7つで**名前・順序とも一致**（想定していた「構造体配列のフィールド不一致」ではなかった）

  出力先 `x4_SingleTrialAnalysisResults/` はいずれも存在
- **コードは変更していないのに再起動で直った** ＝ ファイルの内容ではなく MATLAB の状態が原因

**原因（推定）：**
**MATLAB が古い m3 をメモリにキャッシュしたまま実行していた**可能性が高い。
MATLAB は一度呼んだ関数をメモリに保持するため、関数ファイルを外部エディタなどで
差し替えると、ディスク上の新しい定義とメモリ上の古い定義が食い違うことがある。
今回は角速度ブロックを削除した「関数の中身が大きく変わる」変更だったため、
この食い違いが表面化しやすい状況だった。

> **原因は確定していない。** エラーメッセージを取得する前に再起動してしまったため、
> 再現も検証もできていない。以下は次に同じ症状が出たときの手順である。

**次に同じ症状が出たときの手順：**

1. **エラーメッセージを先に控える。**（今回はこれを取り損ねたため原因が確定できなかった）
2. 再起動の前に、まずキャッシュを疑って以下を試す：

```matlab
clear functions      % メモリ上の関数定義を破棄する
rehash               % パス上のファイル一覧を再スキャンする
which m3_analyze_single_trial -all   % 意図したファイルが見えているか
```

3. `.asv`（MATLAB の自動保存ファイル）が残っていないか確認する。
   エディタで保存し忘れていると、古い定義が実行され続ける。
   前例：`x2_import_data.asv`

**教訓：**
関数ファイルを外部エディタで差し替えた直後に不可解な挙動が出たら、
コードを疑う前に `clear functions` を試す。
そして **再起動する前に必ずエラーメッセージを控える。**
再起動は状態を消すため、直る代わりに原因も消える。

### [2026-07-16] m3：LED キュー検出のバグ ― ready cue を NoGo cue と誤認していた

**発見者：** 加藤 和太郎 (student) / AI (Claude)

**症状：**
x6 の結果テーブルで、**NoGo 試行の `TCueMarker` が全試行 271 で固定**されていた。
Go 試行は 571〜721 とばらついており、プロトコル上 foreperiod は試行ごとに
1.2〜1.8 秒と変わるため、**NoGo でもばらつくはず**だった。

**切り分け：**
NoGo 試行と Go 試行の `LEDData` を描いて比較した（アナログ 250 Hz）。

| チャンネル | Go 試行 | NoGo 試行 | 正体 |
|---|---|---|---|
| ch1 | +5V @ 0 s、−2.5V @ 1.08 s | **完全に同一** | トリガ、および**白の ready cue** |
| ch2 | **+2.45V @ 2.28 s** | **−1.8V @ 2.7 s** | **本物の cue** |

**ch1 が両条件で同一**であることから ch1 = ready cue と判明。
**ch2 だけが条件によって符号を変える**（Go は正、NoGo は負）ため、ch2 が cue チャンネル。

**原因：**
```matlab
led_nogo = Data.LEDData(:, 1) ;              % ← ch1 は ready cue だった
tCueNoGo = find(led_nogo < -2, 1, 'first') ; % ← 1.08 秒（ready cue）を拾う
```
NoGo キューを ch1 から探していたが、ch1 は白の ready cue であり、
プロトコルの「トリガー後1秒間 静止 → 白LED（ready cue）」に対応する固定タイミングだった。
そのため foreperiod によらず常に 271 フレーム（＝1.08 秒）が返っていた。

**解決策：**
```matlab
% ch2 = cue チャンネル。正=Go, 負=NoGo。ch1 は ready cue
led_cue  = Data.LEDData(:, 2) ;
tCueGo   = find(led_cue >  2, 1, 'first') ;
tCueNoGo = find(led_cue < -1, 1, 'first') ;
```

> **閾値に注意。** NoGo パルスは **−1.8V** しかないため、
> 元の `< -2` のままでは ch2 に変えても検出できない。**`< -1` に緩める必要がある。**
> Go パルスは +2.45V なので `> 2` のままでよい。

**副産物：サンプリング周波数が確定した。**
Go cue が 2.28 秒、そのときの `TCueMarker` が 571 フレーム → **250 Hz**。
Go 試行の 571〜721 フレーム = 2.28〜2.88 秒は
「静止 1 秒 + foreperiod 1.2〜1.8 秒」と一致する。**Go 側の検出は元から正しかった。**

**影響範囲：**
- **スイングスピード（②）：影響なし。** `PeakVelTop`・`PeakVelTopX` はキュー時刻に依存しない。
- **反応時間（①）：深刻。** NoGo の起点が 1.6 秒ずれるため、
  `予備実験解析し直し/00_解析し直し方針と作業記録.md` に記録された
  NoGo 関連の数値・結論はすべて再検証が必要。同ファイル冒頭に警告を追記済み。

**教訓：**
> **同じ値が並んだら疑うこと。**
> 「NoGo の `TCueMarker` が全部 271」という**不自然な一致**がバグ発見の入口だった。
> 条件によって変わるはずの量が変わっていない、というのは強い異常信号である。
> 表を眺めるとき、ばらつくべき列がばらついているかを確認する習慣を持つこと。

> **チャンネルの意味を、コードのコメントではなく波形で確認すること。**
> `led_nogo = Data.LEDData(:, 1)` という変数名は「ch1 が NoGo」と主張していたが、
> 実際は ready cue だった。**変数名は検証の代わりにならない。**
