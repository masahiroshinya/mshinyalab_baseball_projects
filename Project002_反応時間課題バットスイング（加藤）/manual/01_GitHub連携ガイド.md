# GitHubとデータを同期する基本の5ステップ

新しく作業を始める時から、GitHubへ反映させるまでの「基本の5ステップ」です。
複数人で同じプロジェクト（GitHub）を触る場合、**「作業前に最新状態にする」**ことと**「作業後に保存して送る」**ことがセットになります。

## Step 1: 作業を始める前に、最新のデータを取り込む（Pull）
作業を開始する前に、共同管理者が何か新しいデータをGitHubにアップしていないか確認し、自分のPCに取り込みます。

```bash
git pull origin main --rebase
```

> **Tip!**
> これを忘れて古いデータを編集してしまうと、あとから合流させるのが大変になります。「作業開始時はまず pull」と覚えておくと安心です。

## Step 2: いつも通りローカルPCで作業する
VS Codeなどを使って、ファイルを作成したり、記事を書いたり、コードを修正します。この段階ではまだGitには記録されず、普通にPCに自動保存されているだけです。

## Step 3: 変更したファイルをリストアップする（Add）
作業が終わったら、GitHubに送りたいファイルの変更を「送信リスト（ステージングエリア）」に乗せます。
以下のコマンドで、変更されたすべてのファイルをまるごとリストに乗せることができます。

```bash
git add .
```
*(※最後の `.` （ドット）は「ここにある変更全部」という意味の記号です)*

## Step 4: 変更をセーブ（確定）する（Commit）
リストに乗せた変更を、あなたのPC内の記録として確定（セーブ）します。このとき「何を変更したか」のわかりやすいメモを残します。

```bash
git commit -m "今日読んだ〇〇の先行研究のメモを追加"
```
*(※ `-m` の後のダブルクォーテーション `"` で囲まれた部分に、日本語で自由に変更内容を書きます)*

### なぜわかりやすいメモ（コミットメッセージ）が必要なのか？
1. **チームメンバー（共同管理者）に作業内容を伝えるため**
   中身を一行ずつ読まなくても「なぜ、何の目的で書き換えたのか」が一目でわかるようにするため。
2. **過去の自分のため（強力な「タイムマシン機能」）**
   何かトラブルがあって過去のデータに戻りたいとき、「この時に何をしたか」が明確であればすぐにお目当てのセーブデータに戻ることができます。
3. **バグやトラブルの原因を特定しやすくするため**
   エラーが起きた際、履歴を遡って原因を特定しやすくなります。

**【良いコミットメッセージの例】**
- `[追加] Kida et al. 2005 の文献ノートを作成`
- `[修正] 文献整理ルールに概要セクションの書き方を追記`

## Step 5: GitHubへ送信する（Push）
ここまできたらあとはネット上に送信するだけです！

```bash
git push origin main
```

---

## 補足：もしStep 5でエラー（[rejected]）が出たら？
あなたが作業をしている間に、共同管理者の先生が先にGitHubへ新しいデータを反映させていた場合、Step 5で安全装置が働きブロックされます（エラーになります）。

その場合は慌てずに、**もう一度ネット側の新しいデータを取り込んでから、再送信**すればOKです（ローカルのデータが勝手に消えることはありません）。

```bash
git pull origin main --rebase
git push origin main
```

## トラブルシューティング：`git pull` が "unmerged files" で失敗する

### 症状（2026-08-04 発生）

```
error: Pulling is not possible because you have unmerged files.
hint: Fix them up in the work tree, and then use 'git add/rm <file>'
fatal: Exiting because of an unresolved conflict.
```

### 原因

過去の `git pull --rebase` の途中でコンフリクトが発生し、その状態が**インデックス（ステージング領域）に取り残されたまま**になっていた。

- `git log` / `git reflog` 上では pull は完走しており、`HEAD` は `origin/main` と一致（＝コミット履歴は正常）
- しかし `git ls-files -u` で確認すると、Project001配下の70ファイルが未マージ状態（`UD` = 手元は変更なし／向こうは削除）として残存
- `.git/MERGE_HEAD` は存在せず、マージ・リベースは進行中ではない（＝「幽霊コンフリクト」だけが残った状態）
- Gitは未マージのエントリが1つでもあると次の pull をブロックするため、毎回このエラーになる

### 切り分け手順

```bash
git status --short              # UD などの未マージ表示を確認
git ls-files -u | wc -l         # 未マージエントリの実数を確認（0以外なら残存）
ls -a .git | grep MERGE_HEAD    # 出力が無ければマージは進行中ではない
git log --oneline -1 HEAD       # HEAD と origin/main が同じなら履歴は無事
git log --oneline -1 @{u}
```

### 解決策

作業ツリー（実ファイル）はそのままで、インデックスだけを `HEAD` の状態に戻す。

```bash
cd ~/mshinyalab_baseball_projects   # リポジトリのルートで実行
git reset                           # --hard は付けない（付けると編集中の内容が消える）
```

このとき、身に覚えのないファイル削除がステージされている場合がある（今回はProject001のsandbox内4ファイル）。他ユーザーのファイルを誤って消さないよう復元してから pull する。

```bash
git checkout -- "復元したいパス"    # HEAD の内容でファイルを戻す
git pull
```

### 注意点

- `git reset --hard` は作業ツリーごと巻き戻すため、未コミットの編集が消える。今回のような「インデックスだけ壊れている」ケースでは **`--hard` なしの `git reset`** を使う。
- `pull.rebase = true` が設定されているため、未ステージの変更が残っていると `cannot pull with rebase: You have unstaged changes.` で止まる。先に commit / stash / 復元して作業ツリーをきれいにしてから pull する。
